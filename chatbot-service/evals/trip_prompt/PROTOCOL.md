# โปรโตคอลการทดลองรอบสุดท้าย (ล็อกก่อนรัน)

ล็อกเมื่อ 2026-10-07 ก่อนรันข้อมูลรอบสุดท้าย ค่าและเกณฑ์ในไฟล์นี้ห้ามเปลี่ยนหลังเห็นผล ถ้าจำเป็นต้องเปลี่ยน ให้บันทึกในหัวข้อ "การเบี่ยงเบนจากโปรโตคอล" ท้ายไฟล์ พร้อมเหตุผลและวันที่ และรายงานผลให้เห็นทั้งก่อนและหลังเปลี่ยน

`report.py` และ `run_eval.py` บันทึก hash ของไฟล์นี้ไว้ใน `config.json` ของแต่ละ run (`provenance.protocol_sha256`) เพื่อให้ตรวจได้ว่าผลถูกสร้างภายใต้เวอร์ชันนี้

## 1. คำถามวิจัย

เมื่อเปลี่ยน prompt ของ generator ทีละเรื่อง (กฎ, ข้อมูลสถานที่, ขั้นวางแผน) บน scheduler และ candidate pool เวอร์ชันปัจจุบัน แผนที่ได้ดีขึ้นกว่า prompt ที่ใช้งานจริง (`v0_baseline`, ในรายงานเรียก `v0_after`) หรือไม่

H0: ไม่มี variant ใดดีกว่า baseline อย่างมีนัยสำคัญเชิงปฏิบัติ → คง prompt เดิม

## 2. การออกแบบ

| รายการ | ค่า |
|---|---|
| variants | `v0_baseline` (= `v0_after`), `v1_rules`, `v2_context`, `v3_plan_first` (นิยามใน `prompts.py`; แต่ละตัวแก้เรื่องเดียว) |
| เคส | 8 เคสใน `cases.py` (c01–c08) วันที่คงที่ |
| รอบ (reps) | 3 ต่อ (variant, เคส) |
| โหมด | `single` เป็นหลัก; `loop` ยืนยันเฉพาะ `v0_baseline` (รายงานแยก ไม่ใช้ตัดสิน variant) |
| generator | `gemini-3.8-flash`, temperature 0.2 (ค่าเดียวกับ production) |
| judge | `claude-sonnet-5.5` ผ่าน `eval_judge.py`, temperature 0.0, blind ต่อ variant |
| candidate pool | cache แท็ก `_final` ที่ freeze แล้ว (`freeze.py`, `cache/manifest_final.json`) ห้าม `--refresh-cache` |
| เพดานโควตา | gemini 350K และ claude 200K ต่อวัน แบ่งรันหลายวันได้ โดยใช้คำสั่งเดิมซ้ำ (resume) |

หน่วยวิเคราะห์คือ **เคส**: เฉลี่ยรอบของเคสเดียวกันก่อน แล้วเทียบระหว่าง variant ในเคสเดียวกัน เทียบเฉพาะเคสที่ทุก variant มีข้อมูลครบ

error จาก infrastructure (โควตา/401/เครือข่าย) ไม่นับเป็นความผิดของ variant และต้องรันซ้ำให้ครบ ส่วน error ของ variant เอง (JSON พังหลัง retry) นับ

## 3. ตัววัด

**ตัววัดหลัก:** ค่าเฉลี่ย judge 1–5 จาก 5 เกณฑ์ (`interest_fit`, `constraint_fit`, `variety_flow`, `day_coherence`, `selection_quality`) rubric และ prompt ของ judge ตามที่อยู่ใน `eval_judge.py` ณ วันที่ล็อก

**ตัววัดรอง (ตรวจด้วยโค้ด จัดตามระดับข้อจำกัดของ Xie et al. 2024):**

| ระดับ | ผ่านเมื่อ |
|---|---|
| Environment | place ID ทุกตัวมีอยู่จริงใน pool และไม่ซ้ำ (output ดิบของ LLM) |
| Hard | must-go ครบในแผนสุดท้าย |
| Commonsense | ทุกวันมีมื้ออาหารในแผนสุดท้าย และ LLM ไม่เลือกที่ปิดในวันนั้น |

รายงานเป็นสัดส่วนรันที่ผ่านแต่ละระดับ และผ่านครบทั้งสาม ร่วมกับ lunch served, pick-quality (interest match, rating เฉลี่ย, thin-review picks) และ raw compliance

งบประมาณและขอบเขตพื้นที่ตรวจด้วย judge (`constraint_fit`) ไม่ได้ตรวจด้วยโค้ด

## 4. เกณฑ์ตัดสิน (ล็อกแล้ว)

เลือก variant ใหม่แทน baseline ก็ต่อเมื่อผ่าน **ทุกข้อ**:

- (a) ค่าเฉลี่ย Δ ระดับเคส ≥ noise floor โดย noise floor = max(0.15, ความแกว่งของ baseline ระหว่างรอบ)
- (b) ชนะมากกว่าแพ้ (ชนะ/แพ้ = ต่างเกิน noise floor)
- (c) ไม่แพ้เคสใดเกิน 0.4
- (d) hard violations ดิบ ≤ baseline + 0.25 ต่อรัน
- (e) must-go ที่หายในแผนสุดท้ายไม่แย่กว่า baseline
- (f) ไม่มีรันที่ล้มเหลวเอง

ถ้าไม่มี variant ผ่านครบ **คง `v0_baseline`**

**ช่วงความเชื่อมั่น:** paired bootstrap สองชั้น (สุ่มเคสแบบคืนที่ แล้วสุ่มรอบภายในเคส) 10,000 ครั้ง seed 20261007 ช่วง 95% ใช้ติดป้ายผลเท่านั้น: ถ้าผ่านเกณฑ์ (a)–(f) และช่วงไม่คร่อม 0 = "confirmed" ถ้าช่วงคร่อม 0 = "tentative" ช่วงนี้ **ไม่ใช่เกณฑ์เพิ่ม** (เพราะ 8 เคสให้ช่วงกว้าง)

รายงานค่าความต่างน้อยสุดที่ตรวจจับได้ (MDE, กำลัง 80%, α = 0.05) ทุกครั้ง เพื่อให้ผลที่ "ไม่พบความต่าง" ตีความได้ถูกต้อง

## 5. การตรวจความน่าเชื่อถือของ judge (รายงานเสมอ)

1. **verbosity**: Spearman ρ ระหว่างความยาวแผนกับคะแนน judge หลังหักค่าเฉลี่ยของเคส (ใน `report.py`)
2. **ความสอดคล้องกับตัวตรวจโค้ด**: คะแนน `constraint_fit` เมื่อ must-go หาย และ `variety_flow` เมื่อมีวันไม่มีมื้ออาหาร ควรต่ำกว่ากรณีปกติ (ใน `report.py`)
3. **test-retest** (ทำแยก ต้องขออนุมัติโควตา): ให้ judge ประเมินซ้ำบน output เดิม ~30 รัน รายงานความต่างเฉลี่ยของคะแนนรวมต่อรัน

## 6. ข้อจำกัดที่ประกาศไว้ล่วงหน้า

- judge ตัวเดียว ไม่ได้ validate กับการให้คะแนนของคน
- generator ตัวเดียว เคส 8 เคสที่เขียนเอง ไม่ได้มาจากคำขอผู้ใช้จริง
- โหมด `single` ไม่รวม regenerate loop ของ production
- ข้อมูลสถานที่ ณ วันที่ freeze เท่านั้น
- คะแนน judge (1–5) ไม่เทียบตรงกับเกณฑ์ผ่าน 0.45 ของ judge ใน production
